# Reviewing the Materialized View Specification

*An analysis of the draft materialized view specification in [apache/iceberg pull request 11041](https://github.com/apache/iceberg/pull/11041), considered as another derived structure attached to Iceberg tables. It asks what ties a storage table's contents to the view definition they were computed from, what writers that do not know about materialized views do to them, and how they behave under compaction and expiration of the storage table and its sources. It finds that the draft can keep materialized views correct without any help from the table specification, given one check on read that the text does not yet require, but that keeping them usable needs cooperation from writers who cannot see the view, and it argues that the table specification can provide what those writers need through general mechanisms that mention no materialized view. Problem identifiers (E24, V14 and so on) refer to the [register of problems](problems.md).*

**Author:** Alex Cruise  
**Updated:** November 19, 2026  
**Status:** draft, not yet circulated; against the pull request's head at commit `7d336c3` (November 19, 2026), and the proof-of-concept implementations in [trinodb/trino pull request 31027](https://github.com/trinodb/trino/pull/31027) at `cdad997` and [apache/iceberg pull request 9830](https://github.com/apache/iceberg/pull/9830) at `bb460f9`, all open

## The draft in brief

A materialized view is an Iceberg view whose version carries a `storage-table` identifier naming an ordinary Iceberg table in the same catalog. Each refresh commits a snapshot to the storage table whose summary holds a `refresh-state` key: a JSON record of the view's `version-id` at refresh time, a `refresh-start-timestamp-ms`, and a list of `source-states` naming each recorded source table by uuid with a `snapshot-id` and a `ref`, and each recorded source view by uuid with a `version-id`. The writer chooses which dependencies to record, and may record none. Since November 18, `ref` is required whenever a source is read through a branch or tag, the implicit `main` included, so an unset `ref` means a pin to `snapshot-id`.

The draft deliberately leaves freshness undefined. After several rounds of review the only definition in the text is that a materialized view is fresh "when the storage table represents the result of the current view query", and Appendix B offers two example criteria, fresh if refreshed recently and fresh if no recorded dependency has changed, without requiring either. Consumers therefore validate on read, comparing what `refresh-state` recorded against the current state of the view and its sources, and that choice disposes of the most apparent concurrency hazards. Under Appendix B's second example, a refresh that raced a `CREATE OR REPLACE` records the old `version-id` and reads as not fresh, and a slow refresh committed after a faster one records older source snapshots and also reads as not fresh. Both cost a wasted refresh, and neither returns an incorrect result.

What remains falls into three groups. A storage table's validity is stated against identifiers, a view version and source snapshots, and the first question is whether those identifiers bind the contents to the definition (Section 1). Materialized view metadata extends structures that older writers rewrite, and the second is what such writers do to it (Section 2). The third concerns the subject of this repository: maintenance creates snapshots without changing data, on the storage table and on its sources, and snapshot-pinned validity must survive it (Sections 3 and 4). A vote to adopt the pull request was called on the dev list on November 16, against head `bf43793`; the head has since moved by six commits, which settle most of Section 3.

## 1. Binding a storage table's contents to the view definition

The protection that validation on read provides depends on the criteria a consumer applies. The text requires `view-version-id` to be recorded but never requires a reader to compare it with the view's current version. A new view version can change the SQL, the `default-namespace` (so that `FROM events` resolves to a different table with identical text) or the schema, and can keep naming the same storage table; a view can also be dropped and recreated while its storage table survives. A consumer applying Appendix B's first example, a staleness window, may then answer queries against the view from the old definition's results until the window elapses. The slow refresh of the opening section is harmless under the first example, since that criterion disregards sources by design, but a change of definition is not.

Neither proof of concept is exposed. Both compare the refresh state's `view-version-id` with the view's current version before any other test, and both create a new storage table on create. On replace they differ:

| | Spark ([apache/iceberg#9830](https://github.com/apache/iceberg/pull/9830)) | Trino ([trinodb/trino#31027](https://github.com/trinodb/trino/pull/31027)) |
|---|---|---|
| Where the version is compared | `isFresh` | Ahead of its grace period |
| `CREATE OR REPLACE MATERIALIZED VIEW` | Rejected, with a comment that the view specification leaves the storage table's fate open | Keeps the storage table and empties it, in a create-or-replace table transaction committed before the new view version, so that the current snapshot carries no `refresh-state` |
| A new view version that leaves the query unchanged, such as a column comment | Rejected: the guard `checkNotMaterializedView` rejects every view commit over a materialized view other than a plain create | Commits an empty append to the storage table that copies `refresh-state` forward with the new `view-version-id` |

The specification permits any of this and requires none of it, since a new view version may change its representations and name any storage table.

The comparison is also weaker than it appears. `refresh-state` records the uuid of every source, but not of its own view, while version ids restart at 1 for each view, so a matching `view-version-id` identifies the definition only while a storage table cannot outlive its view or be named by another. Both gaps close with the rule both proofs of concept already follow, made normative, and a `view-uuid` recorded beside `view-version-id` (candidate text 1 below).

The text also states no consequence of finding a view stale. The vote's summary says that a consumer finding the view stale "must not read from the storage table", but no such sentence appears in the text at `bf43793` or at `498f7a0`, and the commit message of `bf43793` ("soften engine requirements") suggests it was removed. A reader of the text alone may serve the storage table's contents as the view's, under any criteria it chooses.

## 2. Writers that do not know about materialized views

The draft claims compatibility from the reader's side: "a reader that is unaware of materialized views sees the unknown `storage-table` field, ignores it, and evaluates the view query directly." A review comment on November 19 points out that the writer's side differs. A view writer that does not know the field, such as an older Java client running `ALTER VIEW ... SET TBLPROPERTIES` against a catalog in which the client writes the metadata file itself, parses the metadata, drops what it does not recognize and writes the rest back, so the materialized view becomes a plain view and its storage table is orphaned. The comment asks to revisit bumping the view specification's `format-version`, which was declined in February on the ground that nothing in the change breaks a reader.

Since `storage-table` is a field of each view version, not of the view, what an unaware writer does to it depends on how the writer treats fields it cannot parse and on how it makes a new version.

1. **A writer that drops unknown fields**, as the Java parser does, removes `storage-table` from every version it writes back, whether or not its statement creates a version. Every reader then evaluates the query, which is safe. The materialized view is nonetheless lost without notice: aware engines stop using and refreshing it, and nothing records that the storage table belonged to anything, so the table remains until it is dropped manually. This is [E25](problems.md#e25-shared-metadata-is-replaced-whole-by-writers-that-understand-only-part-of-it) in its simplest form.
2. **A writer that keeps unknown fields and makes a new version by copying the current one**, changing only what its statement changes, produces a version that names the old storage table under a new definition. That is the hazard of Section 1, reached without any engine that knows about materialized views, and it is safe only for a reader that compares `view-version-id`, which the text does not require.
3. **A writer that builds a new version from scratch**, as `CREATE OR REPLACE VIEW` does, produces a version without `storage-table`. The storage table is orphaned as in the first case, except that earlier versions still name it, so a rollback reattaches it.

The REST catalog narrows the first case without closing it. A REST client sends updates such as `set-properties` and `add-view-version`, and the server applies them to its own copy of the metadata, so a client's ignorance of `storage-table` cannot remove it from versions the client did not build. An older server that rewrites the metadata through a parser that drops unknown fields has the same defect at the server, and the third case is untouched, since `add-view-version` carries the version as the client built it.

A bump of `format-version` stops an unaware Java writer, whose parser refuses a version it does not support before anything is written, but it stops unaware readers as well, and those are the implementations the compatibility claim was meant to keep: an older engine that would have evaluated the view query correctly would refuse the view instead. A bump applied only to views that have a storage table, leaving plain views at version 1, confines that cost to materialized views, where the reader's fallback is all that is lost. What the case calls for is a fence on writers alone, which a single integer cannot express ([versioning by feature](feature-versioning.md)), and which cannot be added later as a field, since older writers would drop that field too. The bump is therefore the only fence available for a first release. With the version comparison of candidate text 1 in place, none of the three cases returns an incorrect result, which makes the bump a question about liveness and leaked storage tables, to be decided as one.

The reply of February also said that storage tables are distinguished from regular tables by `refresh-state`. A storage table's current snapshot lacks one before its first refresh and after any compaction that does not carry it forward, so the record identifies a storage table only to a reader willing to walk its ancestry, and a maintenance writer is not such a reader. That is the missing marker of Section 7.

## 3. The storage table's refresh state under maintenance

The draft places `refresh-state` in a snapshot summary, and snapshot summaries are not inherited. In the Java implementation, `SnapshotProducer` builds each new summary from the operation's own properties plus running totals carried from the parent; any other key on the parent, `refresh-state` included, is absent from the child. Any maintenance that commits a snapshot to the storage table, whether a compaction through `rewrite_data_files` or a manifest rewrite, therefore leaves a current snapshot with no refresh state. The Trino proof of concept's own source says so: "Snapshot summaries aren't inherited automatically."

Two readings of such a table are available.

1. **Treat the storage table as not fresh.** This is safe, and it means that every compaction of a storage table discards the refresh it compacted. The Spark proof of concept does this: its freshness test, `SparkCatalog.isFresh`, reads `refresh-state` from the current snapshot only and treats its absence as not fresh, and the pull request touches no maintenance action or procedure.
2. **Walk back to the nearest ancestor that carries `refresh-state`.** This is sound only if every snapshot crossed has the `replace` operation, which the table specification defines as adding and removing files "without changing table data". An `append`, `overwrite` or `delete` committed to the storage table directly, by an engine or user unaware that it is a storage table, invalidates the precomputed result, and a walk that crossed it would return incorrect results. Expiration can also remove the ancestor that holds the record, at which point the walk finds nothing and the consumer falls back to the first reading.

Trino met the problem before the draft did and solved it within Trino. Its proof of concept restricts the procedures permitted on a storage table to an allowlist, `OPTIMIZE` and `OPTIMIZE_MANIFESTS` among them, and each of those procedures copies `refresh-state` from the parent onto the snapshot it commits, through a validator that reruns on every commit retry so that a refresh committed concurrently cannot leave a stale record carried onto the new snapshot. A source comment states the stakes: without the copy, "the materialized view's dependency summary is dropped and the next refresh is demoted from incremental to full." The mechanism predates the draft, since Trino's existing Iceberg materialized views carry their `dependsOnTables` summary forward the same way.

Until November 18 the specification therefore depended on a carry-forward obligation that one implementation discharged privately and the text never stated. A storage table compacted by Spark, PyIceberg, a managed maintenance service or any engine other than Trino lost its refresh state, and the loss was silent, because nothing in the storage table's metadata marks it as a storage table that a maintenance writer could check. That is E24 ([metadata attached to data does not survive compaction](problems.md#e24-metadata-attached-to-data-files-does-not-survive-compaction)) and E25 ([shared metadata replaced whole by writers that understand only part of it](problems.md#e25-shared-metadata-is-replaced-whole-by-writers-that-understand-only-part-of-it)) applied to a new kind of metadata, in the form those entries describe: safe by default, expensive in practice, and repaired by each engine for itself.

The head at `bf43793` approached the question without resolving it: a new paragraph said readers "can use the presence of a snapshot with `refresh-state` to distinguish a never-refreshed storage table from one that was refreshed with an empty result", which sends a reader looking for the record beyond the current snapshot without saying what may lie between.

A reviewer raised the case on November 16, and the head at `498f7a0` adopted the second reading for any branch of the storage table. A revision on November 19, `7d336c3`, confined it to `main` and settled its order, so that the sentence "Snapshots written by a refresh operation must set `refresh-state`" is now followed by this:

> The refresh state of a storage table is the `refresh-state` of the closest ancestor of the current snapshot of its `main` branch, including the current snapshot itself, that has one. If any snapshot between that ancestor and the current snapshot has an operation other than `replace`, the storage table no longer reflects that refresh state.

This settles the safety question and most of the liveness question with it. A reader that implements the walk keeps a refresh across a compaction by any engine, so the outcome no longer depends on which engine compacted, and Trino's carry-forward becomes an optimization that spares the walk. The Spark proof of concept will have to follow, but that is a change to an implementation, not a gap in the text. The version of `498f7a0` said "the most recent snapshot", which admits an order by timestamp as well as by ancestry, and the table specification does not require timestamps to increase; "closest ancestor ... including the current snapshot itself" removes the ambiguity. Confining the rule to `main` leaves other branches of a storage table, such as one used for write-audit-publish, with no defined refresh state. Two points of wording remain:

1. **The consequence is descriptive.** "No longer reflects that refresh state" describes the storage table without saying what a reader does, while the first sentence still defines its refresh state as the record that no longer applies. The rule needs a consequence addressed to readers: such a storage table has no refresh state, and an engine treats the storage table as never refreshed.
2. **Expiration is covered only by implication.** When expiration removes the snapshot carrying the record, nothing reachable carries one, and the storage table reads as never refreshed under the paragraph on storage table creation. The outcome is right, but the text reaches it by inference, and that paragraph's "presence of a snapshot with `refresh-state`" does not refer to the new rule, though read on its own it licenses the unconditional walk that Section 6 measures as unsafe.

Carry-forward itself was not adopted, and with the walk normative its absence costs only the walk (Section 6).

## 4. Source rewrites and staleness

Under Appendix B's second example, a consumer judges a materialized view fresh only if each recorded source table's `snapshot-id` is still the head of its `ref`. A compaction of a source moves the head without changing data, so the view becomes stale, and the next query either recomputes the view or waits for a refresh. Expiration was raised in review in September, and the reply was that an expired snapshot cannot be the head of any branch, so a view whose recorded snapshot has expired is not fresh. That is correct, but the case it does not address is the one in which nothing expired and the only intervening commits were rewrites. A reviewer suggested in April comparing against "the latest data-changing snapshot" instead, which addresses that case but was not adopted.

This is [V14](problems.md#v14-each-rewrite-disables-a-snapshot-pinned-index-until-it-is-rebuilt) for materialized views. The index specification's reference implementation declines to use a snapshot-pinned index across any non-append snapshot, for the same reason and at the same cost, and a materialized view over a table compacted nightly is stale after each compaction until it is refreshed. The repair is the ancestry rule of Section 3 applied to sources: a recorded source snapshot is equivalent to the current head when every snapshot between them has the `replace` operation, and when expiration has removed part of the chain the consumer cannot establish this and must treat the source as changed. A `replace` snapshot can also carry a `constraint-statuses` update in version 4, which does not change data and is therefore harmless under this rule.

Since the draft declines to define freshness, the fitting contribution is not normative text but a third example for Appendix B, "fresh if dependencies are unchanged up to content-preserving rewrites", stating the rule and its fallback. That gives engines a shared and explicitly sound criterion without reopening the definition of freshness, which the review threads show to be the most contested question in the draft. It also bears on incremental refresh, where Trino's comment quoted above shows that losing the recorded state already costs a full refresh.

## 5. Lesser observations

- **Regressing refresh state.** Two refreshes that race both succeed, since each commits to the storage table under ordinary optimistic concurrency, and the later commit wins even if it read older sources. Validation on read makes this safe, and it wastes the newer refresh. A refresh could validate that no concurrent commit to the storage table recorded a newer `refresh-start-timestamp-ms`, although that compares writers' clocks.
- **Storage table changes across view versions.** What happens to the old storage table when a new view version names a different one, or when the view is rolled back to a version that names an earlier one, was asked in September and remains open. Since November 19 the text treats a new storage table as routine ("a full refresh that writes a new storage table") and requires the new one to carry over the old one's configuration, but says nothing about the old one, which a rollback may still name. It is the reachability problem of the [note on index reachability](../proposals/index-reachability.md) in another form, and with Section 2 it is the second route by which storage tables are orphaned.
- **Queries that read the clock.** A view query that calls `current_timestamp()` or `now()`, such as one selecting the last seven days of events, changes its result as time passes, though no source changes. This is often the purpose of the view, since a seven-day window is meant to advance, but the specification has no means of recording the dependency.
  - Appendix B's second example judges such a view fresh for as long as its recorded source snapshots remain the heads of their refs, because the refresh state records the snapshots the query read and not the time it was evaluated for. The same is true of anything else the query reads from its evaluation context and the refresh state does not record, such as the session's time zone, the current user, or a function whose definition has changed.
  - Appendix B's first example, a staleness window, compares the time of the refresh with the present. Since it cannot know how the query uses the time, it bounds the error only by the window.
  - A declaration in the view version, stated by the author or detected by the creating engine, would tell every engine judging freshness that the query reads the current time, and candidate text 5 sketches one. An engine that can determine how the time is used could then improve on a window. A query that reads `current_date` changes its result only at a day boundary, in the time zone the query was bound to (which the view would then need to record as well), and a query that reads the time in several places changes at the earliest of their boundaries ([note on expression analysis](../proposals/expression-analysis.md#31-graded-coeffects-the-current-time)).
  - Short of a declaration, the text could say that a criterion based on recorded dependencies applies only to a query whose dependencies are all recorded. That requires engines to analyze the query for what it reads, and since the view query is SQL in an engine's dialect, each engine can do so only for its own representation.

## 6. Measurements

The [commit-history harness](../../commit-histories) models a materialized view `SELECT * FROM src` with storage table `mv`, refreshed at the start, and enumerates every interleaving of one to three operations drawn from:

- source appends, compactions and deletion-vector deletes;
- refreshes;
- storage table compactions, with and without carrying `refresh-state` forward;
- a deletion-vector delete on the storage table by an engine that does not know it is one;
- expiration on either table.

That is 4,673 histories. After every step a reader resolves the storage table's refresh state under one of three rules and judges freshness under one of two criteria, and uses the storage table if both agree; the probe is unsafe when it uses the storage table and the storage table's rows differ from the source's. Commits run under [prose fixes 1 and 2](prose-fixes.md#1-retry-conditions-for-deletion-vectors-and-column-files), so that errors in table-level retries do not contaminate the comparison. The view query is fixed and no view version changes, so the slice models Sections 3 and 4, not Sections 1 and 2.

| Refresh-state rule | Recorded snapshot is the head (Appendix B, Example 2) | Unchanged up to replaces (Section 4's proposed example) |
|---|---|---|
| Current snapshot only (the Spark proof of concept) | usable 58.5%, unsafe 0 | usable 64.7%, unsafe 0 |
| Nearest ancestor, unconditionally (the "presence" sentence read alone) | usable 68.6%, unsafe 1,606 | usable 77.5%, unsafe 2,048 |
| Nearest ancestor across `replace` (`498f7a0`) | usable 63.4%, unsafe 0 | usable 70.8%, unsafe 0 |

Percentages count probes, one per step of each history, reads included, so they compare the rules and do not estimate any deployment's experience. Three conclusions follow.

1. **The ancestry rule adopted at `498f7a0` was needed, and it is enough.** The unconditional walk is unsafe after a single non-`replace` write to the storage table, such as the deletion-vector delete above. Under the ancestry rule no probe in the slice is unsafe, under either freshness criterion.
2. **The walk recovers nearly everything carry-forward would.** Among the 1,249 histories in which the storage table is compacted without carrying the state forward, a reader of the current snapshot only can use the view at 53.1% of probes, and a reader applying the ancestry rule at 64.4%. Among the 1,249 in which compaction carries it forward, both reach 64.9%. The remaining half point is expiration, which removes the snapshot the walk would have found while a carried-forward record stays on the current snapshot. Carry-forward can therefore remain optional (candidate text 3).
3. **Section 4's third example costs nothing in safety.** Judging a source unchanged up to `replace` snapshots raises availability under the ancestry rule from 63.4% to 70.8%, with no unsafe probe, because source compactions no longer make the view stale.

## 7. Decoupling and its limits

The draft is written as an extension of the view specification, and its authors treat independence from the table specification as a goal: a storage table is an ordinary Iceberg table, a reader unaware of materialized views ignores `storage-table` and evaluates the view, and nothing in the table specification mentions views at all. The goal is sound, and the question the findings above raise is how far it can be held. They divide cleanly on that question, along the line between safety and liveness, liveness meaning here progress at reasonable cost, which for a materialized view amounts to being usable most of the time instead of recomputed on every query.

### Safety without coupling

Every rule above that protects correctness is a rule for consumers of the materialized view, and each relies only on guarantees the table specification already gives to anyone: that snapshots form an ancestry in which a `replace` snapshot leaves table data unchanged, and that a snapshot which has expired is not the head of any reference. Validation on read is of this kind, and so are its refinements in Sections 3 and 4, the ancestry walk and the treatment of an expired recorded snapshot as a change. They make the view specification depend on the table specification, which it already does by recording snapshot identifiers, and they put no obligation in the other direction. The table specification can remain ignorant of materialized views, and every consumer that follows these rules still returns only correct results.

### Liveness and parties unaware of the view

The costs found above, from a storage table losing its refresh state when compacted to an incremental refresh defeated because expiration removed the snapshot it would have started from, can each be avoided only if some writer or maintainer of an ordinary table behaves differently because a materialized view depends on that table. Three such parties appear:

1. a maintenance writer committing a `replace` snapshot to a storage table, which should carry `refresh-state` forward (candidate text 3);
2. any writer to a storage table, which should confine itself to refreshes and content-preserving rewrites;
3. the expiration process of a source table, which should retain the snapshots that incremental refresh will start from.

An obligation that falls on a party unable to determine whether it applies cannot be enforced in practice, and none of these parties is given a means of determining it. A storage table is marked as one only by a pointer in view metadata, which a table writer never reads, and a source table records nothing about the views that read it. Stating these obligations in the view specification alone therefore leaves them unenforced, which is the present situation: Trino honors the first because it implements both the materialized view and the maintenance procedures, and no other engine does. Keeping a materialized view usable under ordinary maintenance requires that the table specification tell table writers something, and in that sense some coupling is necessary. The general form of the argument, that safety can be had by validation alone while liveness needs the cooperation of writers, and cooperation needs them to know, is not peculiar to materialized views. It is the argument of [E17](problems.md#e17-maintenance-learns-what-to-keep-only-from-snapshot-metadata) and E25, and [V13](problems.md#v13-conforming-version-4-maintenance-may-delete-indexes) shows the failure that results when it is ignored.

### Generic coupling

The table specification need not mention materialized views to give these parties what they need. Two mechanisms, each already wanted for other reasons, would cover all three obligations.

1. **A carry-forward rule for attached metadata.** A declaration, per summary key, blob type or property, of whether a writer that does not understand it should copy it onto a snapshot that leaves data unchanged or should drop it. PNG answers the same question with its copy-safe bit; it is the carry-forward dimension of the [note on contracts](README.md#appendix-b-dimensions-of-the-contract) and the subject of E25. Declared copy-on-`replace`, `refresh-state` would survive any conforming maintenance writer, and Trino's private `carryForwardMaterializedViewDependencies` would become the general behavior. Statistics files and data-file-scoped index blobs are other users of the same rule.
2. **A declaration of what depends on a table.** A place in table metadata where something outside the table can record that it depends on the table and what it needs from it, for maintenance to read before it acts. For a storage table the declaration says that writes other than refreshes and content-preserving rewrites invalidate a dependent; for a source table it names snapshots that a dependent still needs. This is the declaration of discovery roots in [version 4 ask 3](v4-asks.md#3-declaring-what-a-snapshot-depends-on), extended from structures that maintenance must spare to dependents whose needs maintenance should respect. Index files under the table location (V13) are one user, and materialized views are another.

Iceberg already has a partial instance of the second mechanism. A refresh could place a tag on each source snapshot it read, with `max-ref-age-ms` set to bound how long the tag survives, and snapshot expiration already retains snapshots that tags reference, so the snapshot an incremental refresh starts from would be kept without any change to either specification. The cost is that a refresh then commits to every source table it reads, which requires write permission on the sources and contends with their ordinary writers, and the tags it leaves behind must be removed when the view is dropped. Those costs are high enough that tags are not a satisfactory mechanism, but they show that the second mechanism generalizes something Iceberg already accepts and is not a new kind of coupling.

A declaration of dependents reverses the direction in which the draft records dependencies, so that the source names the view as well as the view naming the source, and the reversed record has to be written by the dependent into a table it otherwise only reads. Every change to a dependent's needs (the creation or removal of a view, and for retained snapshots every refresh) becomes a write to the source, with the permission and contention costs already counted against tags, and a dependent that disappears without cleaning up leaves its declaration behind. A view dropped by an engine that does not know to remove the declaration, or by a catalog that drops the view without touching its sources, is the ordinary way that happens. Version 4 ask 3 meets the same objection for its own declaration and answers that a stale declaration should cost an early refusal only its earliness. The corresponding answer here is that staleness never costs correctness: a stale marker on a former storage table restricts writes that would now be harmless, and a stale retention keeps snapshots that no reader will use. Both are refusals or leaks, not wrong answers, but the leak grows without bound, since nothing in the source table can tell a live dependent from a dead one.

A lease answers this better than cleanup does. If each declaration carries an expiry that the dependent renews whenever it refreshes, a declaration whose dependent has gone lapses by itself, and maintenance needs no way of resolving the dependent through a view catalog that may not be its own, which would reintroduce the coupling this section set out to limit. The cost falls on the dependent: a view not refreshed within its lease loses the retained snapshot, and its next refresh is a full one, a loss of liveness with safety intact. Expiry has to be judged against some clock, and comparing a lease's timestamp against the clock of a maintenance process carries the caveat of [E9](problems.md#e9-orphan-removal-races-with-commits-and-compares-clocks), but the asymmetry is tolerable here, since a lease that lapses early costs a full refresh and one that lapses late costs storage for longer than necessary. Tags with `max-ref-age-ms` are already a lease in this sense.

Who chooses the lease's period remains open, and the choice ties retention on the source to the view's refresh schedule. A lease renewed when a refresh commits must outlast the interval between refreshes plus the duration of the next one, or the snapshot the next refresh starts from may expire while that refresh is running, and a view refreshed less often than its lease period never refreshes incrementally at all. The party that knows the schedule is the view's writer, which argues for the dependent requesting the period with each renewal. The party that pays for the retention is the owner of the source table, whose storage holds the snapshots, and a dependent free to request any period could pin snapshots indefinitely by asking for a long one. One arrangement is for the dependent to request a period against a ceiling that the source table declares in its own properties, with maintenance honoring the lesser of the two, so that each party controls the quantity it is responsible for. The ceiling is itself a new table property, and so a further piece of coupling, but of the generic kind: it says nothing about materialized views, and it is set by the owner of the table it governs for the benefit of any dependent that declares itself. The draft offers nowhere to put the requested period, since the standardized staleness window it once had, `max-staleness-ms`, was removed for want of agreement among engines, and an engine-specific view property would serve only that engine's renewals.

The view specification, then, can and should stay decoupled for correctness, which is where most of the review's effort has gone. The coupling needed for the view to be usable belongs in the table specification as general extension points with several users, of which materialized views are one, and those extension points coincide with requests this repository makes for other reasons.

## Candidate text

These sentences belong in the view specification and use only metadata the draft records, apart from the new fields in the first and fifth. They govern an engine resolving a materialized view, not anyone reading the storage table as an ordinary table, which remains legitimate.

1. An engine evaluating a materialized view must not use the view's storage table in place of the view query unless the `refresh-state` it relies on records the view's `view-uuid` and its `current-version-id`, whatever its freshness criteria. This needs a new required field, `view-uuid`, in the refresh state; since the specification is not yet adopted, it can be required from the start, and the proofs of concept would need only to write it (Sections 1 and 2).
2. The refresh state of a storage table is the `refresh-state` of the closest ancestor of the current snapshot of its `main` branch, including the current snapshot itself, that has one, provided every later snapshot has operation `replace`. If a later snapshot has any other operation, or no such ancestor remains, the storage table has no refresh state, and an engine must treat it as never refreshed. The sentence on using "the presence of a snapshot with `refresh-state`" would cite this rule. This is the rule at `7d336c3` with a consequence addressed to readers.
3. (Optional.) A writer committing a `replace` snapshot to a table it knows to be a storage table should copy `refresh-state` from the parent snapshot, re-reading the parent on each retry.
4. (For Appendix B, as an example.) A materialized view is fresh if, for each recorded source table, every snapshot after the recorded `snapshot-id` and up to the head of its `ref` has operation `replace`; if any has another operation, or the chain cannot be established because a snapshot in it has expired, the source has changed (Section 4). The criterion applies only to a view whose query reads nothing beyond its recorded sources, and in particular not the clock (Section 5).
5. (For Appendix B, as an example, with one new field.) A view version may carry `context-dependencies`, a list naming what its query reads from the evaluation context beyond its sources, set by the author or by the engine that creates the version after analyzing the query.
   1. **Entry.** This text defines one entry, `current-time`, with an optional `granularity` of `day` or `hour` and a required `time-zone`. Together they assert that the query's result depends on the current time only through that time truncated to the granularity in that zone.
   2. **Refresh.** An engine refreshing a view that declares `current-time` must bind the query's current time to the refresh's `refresh-start-timestamp-ms`.
   3. **Freshness.** Such a view is fresh if criterion 4 holds for its sources and the present falls in the same granularity interval, in the declared zone, as `refresh-start-timestamp-ms`. Without a granularity, it is fresh only within whatever staleness window the consumer accepts (Appendix B's first example).
   4. **Absence.** An empty list asserts that the query reads nothing beyond its sources, which is the condition criterion 4 requires. A version without the field asserts nothing, and an engine may apply criterion 4 to it only after analyzing the query itself, so a writer that drops the field (Section 2) loses the claim without making a false one (Section 5).

## Open questions

- Whether Spark's `rewrite_data_files` and `rewrite_manifests` expose a hook through which an extension could set summary properties. If not, candidate text 3 is not satisfiable by Spark without a change to Iceberg's actions.
- Whether `IncrementalAppendScan` fails or skips when its range includes `replace` snapshots, which a reviewer asserted in September and which determines how much incremental refresh suffers from Section 4.
- Whether Trino's incremental refresh crosses `replace` snapshots on a source.
- Whether the view version should declare what its query reads from the evaluation context, at least the current time, and whether engines can detect that in their own dialects reliably enough to set the declaration when a view is created (Section 5).
- Whether any engine writes to storage tables with operations other than `replace` outside a refresh, for example a `DELETE` for privacy compliance. The ancestry rule keeps such a write safe, at the cost of the refresh it invalidates, but it would make the second obligation of Section 7 contentious.
