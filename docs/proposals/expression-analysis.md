# What an Expression Reads and What It Can Do

*A proposal, written for the Iceberg UDF sync, on how a feature should decide which expressions it admits and what its consumers may rely on them for.*

**Author:** Alex Cruise  
**Updated:** November 19, 2026  
**Status:** draft for discussion; specification text is quoted from apache/iceberg `main` at commit `037d8af`

## Summary

Version 4 of the table specification admits expressions in write defaults, `check` constraints and statistics over expressions, and proposals in flight add them to index definitions and to the bodies of user-defined functions. Each feature writes its own rule about which expressions it accepts, and the UDF specification summarizes a function's behavior in one flag, `deterministic`. That flag is too coarse. What a feature needs to know is what an expression reads from its context (the clock, the session's time zone, the engine's Unicode tables and regular expression dialect, other tables, the order in which it is evaluated) and what evaluating it can do (produce a null, raise an error), and different features tolerate different subsets of both.

This note proposes that the expressions specification define that analysis once, over the whole expression tree; that every consumer refuse an expression it cannot analyze; that each feature say which properties it permits and what a consumer may rely on an expression for; and that a stored expression record the environment it was written against, defaults included, so that an engine with the same environment can rely on it. The urgency comes from a change of role. Expressions entered Iceberg as things writers evaluate, where a misunderstanding fails a write, and are becoming things planners trust, where a misunderstanding returns a wrong answer quickly.

The changes fall into [three phases](#changes-in-three-phases). The first fences what the specifications already admit and needs almost no new metadata, and it is the one that should land before planners begin to rely on stored expressions. The second defines the vocabulary and declarations that let features admit more, and the third lets functions that depend on their environment into stored uses by recording that environment.

## What we are asking

1. **That the [expressions specification](https://github.com/apache/iceberg/blob/037d8af/format/expressions-spec.md) define a small vocabulary of properties** describing what an expression reads (its *coeffects*) and what its evaluation can do (its *effects*), with rules for computing both over a whole expression tree, and a way to record with a stored expression the values of the context it reads.
2. **That every function the specifications define, and every user-defined function, declare those properties**, with an undeclared property assumed to be the worst case.
3. **That every consumer of an expression analyze every node, and refuse an expression containing anything it cannot analyze**, with the consequence of refusal (fail, or ignore and degrade) fixed by the feature that carries the expression.
4. **That every feature that uses expressions specify which computed properties it permits, and how those properties bear on reliance**: what a consumer may conclude or do on the strength of an expression that passes, and what it does with one it refuses.

The labels *effect* and *coeffect* come from the programming languages literature and are not essential; any pair of names for "what it reads" and "what it can do" would serve. The analysis is the proposal, and the vocabulary is negotiable.

## Expressions are already in the door

The expressions specification describes itself as deliberately simple: constants, field references, and function applications, with complexity "pushed to the functions that are called", which are either a short list of portable functions or user-defined functions "that can use the full range of SQL capabilities". The structure is simple, but a node of it can hold any function a catalog defines. Version 4 admits expressions in several places, each of which has written its own rule about which expressions are acceptable:

| Where | What the table specification says about admissible expressions |
|---|---|
| [`write-default`](https://github.com/apache/iceberg/blob/037d8af/format/spec.md#default-values) | Field references are not allowed; constants and function applications are |
| `initial-default` | Must always be a literal |
| [`check` constraints](https://github.com/apache/iceberg/blob/037d8af/format/spec.md#check-constraint-expressions) | Must be "pure", its result depending "only on the values of the fields it references in the row", with no side effects; a UDF used in one "must declare `deterministic` as true" |
| [`expr-value` stats-only fields](https://github.com/apache/iceberg/blob/037d8af/format/spec.md#stats-only-fields) | Must use only ID references; a writer that does not support an expression sets its stats to null |
| Scan planning filters and residuals in the REST protocol | Named references; nothing about which functions |

Proposals in flight add more: input expressions on index blobs ([Puffin proposal, Section 7.8](puffin-blob-types-and-compaction.md#78-expressions-as-inputs)), derived columns in the index specification, and expressions in the bodies of user-defined functions themselves.

Each of these rules is reasonable, and each is a special case of a question that none of them asks in general: what does this expression depend on, and what can happen when it is evaluated? The `check` constraint rule comes closest. "Its result must depend only on the values of the fields it references in the row" is a statement about what the expression reads, and "no side effects" is one about what it can do, so the table specification already performs the analysis this note proposes, informally, for one consumer.

## Determinism is one coeffect, and not the most useful one

The [UDF specification](https://github.com/apache/iceberg/blob/037d8af/format/udf-spec.md) gives each definition version an optional `deterministic` flag, defaulting to false. A single boolean has to stand for several distinct facts, which matter to different consumers in different ways.

- `current_timestamp()`, or `now()`, reads the clock, and is deterministic given the clock. Where it appears decides whether that is acceptable:
  - As a `write-default` it is acceptable, because whatever value the writer computes is stored and every reader afterward sees the same one. When and how often the writer computes it is another matter, which the table specification leaves open: it says only that the expression is evaluated for records written without the field. A writer that evaluates it per row gives the rows of one insert different values, and one that evaluates it per statement gives them one. A retried task, or a statement planned again after a commit conflict, evaluates it again, so the stored value can postdate the first attempt by however long the retries took, while a retry that reuses data files already written keeps the earlier value. The clock is read once per evaluation, and the number of evaluations is a coeffect of the schedule, as it is for `random(seed=4)` below.
  - As an `initial-default` it is useless, since readers would evaluate it retroactively and disagree.
  - In a query, engines usually fix its value at the start of execution, which makes it consistent across the rows of one query and does nothing for the next. Fixing it that way already treats the current time as an environment parameter, bound once per query as a session binds its time zone. An Iceberg snapshot never changes, so a query against a pinned snapshot ought to be repeatable, and because each run binds the current time afresh, the query returns a different answer on every run against the same immutable data. A run that binds it to the first run's value repeats the first run's answer.
  - In a materialized view's query it is often wanted, since a view over the last seven days is meant to slide, but nothing in the view's metadata says so. The second example criterion in Appendix B of the [draft materialized view specification](https://github.com/apache/iceberg/pull/11041) judges the view fresh because no recorded source snapshot has moved, while the time, which the refresh state does not record, has. An analysis that detects the dependency, or a declaration of it, lets an engine refresh such a view when its window moves.
- A function of a local date or time reads the session's time zone as well, and one that converts between zones reads the implementation's time zone database, whose rules change several times a year.
- `upper()` and `lower()` over non-ASCII text read the implementation's Unicode tables, so two engines on different Unicode versions can disagree about the same input while each is deterministic by its own lights.
- `regex_match()` reads the regular expression dialect, and dialects disagree about backreferences, lookaround and what `.` matches outside ASCII.
- Floating-point arithmetic reads more than its operands. IEEE 754 rounds each basic operation correctly, so `a + b` over doubles is reproducible, but floating-point addition is commutative and not associative, so a sum of three values depends on the order of the additions, and a sum over many values on the order in which it visits them. Kahan's compensated summation shows how sensitive this is within a single implementation: it recovers most of the precision a naive running sum loses purely by changing what is added to what, and a compiler that assumes associativity simplifies its compensation term to zero and discards it. Transcendental functions such as `exp` and `log` add a dependency on the math library, since the standard recommends correct rounding for them without requiring it, and libraries differ in the last bit. The expressions specification has no aggregates, but a materialized view's query does, and an incremental refresh that adds new rows into a stored `sum` over doubles combines them in a different order from a full refresh and can store a different answer.
- `random()`, or a generated UUID, reads a source of entropy, and is the case the word "nondeterministic" describes best.
- `random(seed=4)` reads no entropy, but its seed does less than the syntax suggests. Evaluated literally, with a fresh generator for each call, it returns the same first value every time and is a constant. Engines instead create a generator once, commonly per task, and draw from it row by row, so each row's value depends on the generator's state: how many draws preceded it, which follows from how the work was split and the order in which rows were visited. The seed is better understood as an environment parameter that initializes that state, together with the generator algorithm, which differs between engines. Both can be recorded as context (see below). The position in the sequence cannot, so an engine that splits the work differently, or retries a task, assigns the same values to different rows, and the expression is reproducible only as a whole run on one evaluator under one schedule, which no stored expression can assume.
- A lookup in another table reads state outside the row and outside the expression, which changes on its own schedule.

Each is a dependency on context, a coeffect, and treating them as one bit forces the wrong answer somewhere. Marking `current_timestamp()` nondeterministic excludes it from defaults whose meaning is well defined; marking `upper()` deterministic admits it into a stored index expression that a reader on another Unicode version will evaluate differently, and an index that matches a query's literal under different case-folding rules from the ones it was built with excludes files that contain the rows sought. What most stored expressions need is *reproducibility across evaluators*, the same answer from every implementation that evaluates the expression at any later time. Determinism is the special case of reproducibility in which only one evaluator ever runs.

Effects need the same treatment. Whether an expression can produce a null, raise an error, or fail to terminate matters to every consumer, and the specifications already depend on some of it piecemeal. The expressions specification reasons this way about its own comparisons, noting that `get_item` may return a null and `multiply` may produce a NaN, and giving both a fixed meaning through null-safe comparison. A writer must fail when a required field's `write-default` evaluates to null. The UDF specification's `return-nullable` and `on-null-input` are declarations of null behavior, and `on-null-input: return-null` licenses an engine to rewrite `WHERE f(a,b) > 0` as `WHERE a IS NOT NULL AND b IS NOT NULL AND f(a,b) > 0`. Division can raise an error, which is harmless in a `write-default`, where the error fails the write, and needs a stated meaning in a `check` constraint, where it is unclear whether an error is a violation. The UDF specification's `secure` flag is in the same family: a secure function's errors must not reveal what it read, which is a constraint on its effects.

A useful starting vocabulary, offered for the sake of argument and expected to change:

| Coeffects: what evaluation reads | Effects: what evaluation can do |
|---|---|
| Fields of the current row, by ID | Produce a null |
| Rows other than the current one, or other tables | Raise an error (and which kinds) |
| The current time, at a granularity: a day, an hour, the engine's finest resolution | Fail to terminate, or exceed a resource bound |
| Session context: time zone, locale, user | Produce a NaN |
| Implementation tables: Unicode, time zone database, regular expression dialect, math library | Reveal what it read through an error or timing |
| A source of entropy | Write anything outside its result |
| Evaluation state: how many times, and in what order, it has been evaluated or its inputs combined | |
| The definition of a function it calls, at a particular version | |

## The analysis applies to the whole tree

Expressions nest without limit, so a rule that inspects the outermost function inspects almost nothing. `upper(trim(coalesce(my_udf(), 'n/a')))` is built of string functions whose properties are well known, except for `my_udf`, and if `my_udf` reads the clock, so does the whole expression. The rule for computing an expression's properties follows the structure the expressions specification already defines:

1. A constant reads nothing and does nothing.
2. A field reference reads that field of the current row.
3. An application reads whatever its function reads, together with whatever each of its arguments reads, and can do whatever its function can do together with whatever each of its arguments can do, less what the function discharges.
4. A function may declare that it discharges an effect of some of its arguments. `coalesce` discharges the possibility of a null in its earlier arguments if its last argument cannot be null, and `if_else` discharges the effects of the branch it does not take only if the specification guarantees that it does not evaluate that branch.
5. A function without a declaration reads everything and can do everything.

Some coeffects carry a parameter, and "together with" then needs a rule for combining parameters. The current time is the clearest case. `current_date` reads the time at the granularity of a day, in the session's time zone, `now()` reads it at the engine's finest resolution, and `date_trunc('hour', now())` reads it at an hour, because truncation discharges the finer granularity of its argument in the way rule 4 describes. The granularity says how long a result may be memoized: the value of an expression that reads only `current_date` holds until midnight. An expression that reads the time in several places can change at the next boundary of any of them, so its result holds until the earliest such boundary. When the granularities nest, as hours do within days in one time zone, that is the boundary of the finest, and the combination is simply the shortest granularity in the tree. When they do not nest, as with weeks and months, or days in two time zones, the earliest boundary can come sooner than any one granularity suggests, and the combination is the union of their boundaries. (In the coeffects literature, a coeffect with a parameter of this kind is called graded.) A materialized view whose query reads the time is the consumer that most needs this, since the combined granularity tells an engine when the view will go stale without a change to any source.

Because the computation runs over the abstract structure, it is independent of syntax. The JSON serialization of the expressions specification, the REST protocol's deprecated term encoding, and whatever encoding comes next all denote the same trees and yield the same properties. Syntax matters for interchange and for unambiguous function references, which the expressions specification already settles, and the analysis does not depend on which syntax won.

The abstract structure already contains one effect boundary. The expressions specification divides expressions into value expressions and predicates, and requires that a predicate produce true or false: a value expression is not a valid predicate even when it returns a boolean, so `is_empty(str_col)` is rejected "because it may produce `null`" and `is_empty(str_col) = true` is accepted. Comparisons must be null-safe, and predicates use 2-valued logic, so an engine that implements SQL's 3-valued logic has to settle what a null means before it passes the expression on. `x < 10` becomes `x < 10 AND x IS NOT NULL` in a `WHERE` clause and `x < 10 OR x IS NULL` in a `CHECK` constraint, "rather than depending on context to interpret a null result". In the terms of this note, the boundary between a value expression and a predicate discharges the effect of producing a null, and the rewrite resolves, when the expression is written, a dependency on which feature will consume it, the same move the next section proposes for environmental defaults. The boundary is conservative, treating every value expression as possibly null whatever its function declares, which errs in the safe direction. It covers nulls and NaNs and nothing else: the requirement that every predicate produce true or false says nothing about a comparison whose operand divides by zero and raises an error.

The tree also fixes the order of evaluation, and an engine that rewrites it, to fold constants, to regroup operands for a vectorized kernel, or to match a query's term against a stored expression, may use only identities that hold for the functions involved. Over doubles, `(a + b) + c` and `a + (b + c)` are different expressions. Over integers they are the same only if overflow wraps, since where overflow raises an error, as in ANSI mode, one grouping can fail where the other does not. Which algebraic laws a function obeys is a property it can declare, as `on-null-input` declares a law about nulls, and a rewrite that relies on an undeclared law has assumed the best about a function it does not understand.

The body of a user-defined function is the one place the analysis cannot see into, since it is SQL text in one or more dialects. A UDF's declarations must therefore cover its body, including every function the body calls, and a consumer trusts them as it trusts the function's signature. An engine able to parse a dialect may check the declarations against the body, and should refuse a definition whose body reads or does more than it declares. Since UDF definitions are versioned, an expression's computed properties can change when a function it calls is redefined, and a stored expression should record the definition versions it was analyzed against, or be analyzed again when they change. The table specification currently declines this for `check` constraints: a UDF used in one "is expected to preserve its behavior across definition versions", and readers and writers "are not required to detect behavioral changes". That is tolerable while nothing relies on a constraint's status to change a query's answer, and the section on refusal below explains why it will not remain tolerable.

## A recorded context can be relied on

Many of the coeffects above are dependencies on an environment that holds still for the length of a query and differs between engines: the collation, the regular expression dialect, the Unicode version, the time zone database release, the session time zone, and switches such as ANSI mode that decide whether an overflow raises an error or wraps. An expression that reads one of these is underspecified, since its text omits values on which its result depends. If the values it was written against are stored with it as implicit parameters, the dependency becomes an argument, and the expression reads nothing from its environment that it does not carry along. (Implicit parameters are one of the motivating examples in the coeffects literature, in Petricek, Orchard and Mycroft's 2013 paper that introduced the term.)

A consumer can then rely on the expression if it can evaluate it under the recorded context, either because its own environment matches or because it can construct one that does. An engine that runs in ANSI mode by default can usually evaluate in the other mode on request, and one that bundles a library for a named regular expression dialect can evaluate that dialect wherever it runs. A consumer that can do neither treats the expression as one it cannot analyze and takes the feature's course for refusal. Reproducibility across evaluators thereby stops being a property of a function alone and becomes a relation between the recorded context and the evaluator, and a feature's test changes from "reads no implementation tables" to "reads only what it records". `upper()` over non-ASCII text, excluded from every stored use under the first test, is admitted under the second wherever the Unicode version is recorded, and a reader with different tables ignores an index built on it as it would any blob it cannot use.

Four conditions make this work:

1. **The recorded values need names that implementations agree on**: a Unicode version, an IANA time zone database release such as `2026a`, a collation as a locale tag with the version of its rules, a dialect or mode by a name the expressions specification registers. A consumer can compare names but cannot check that its environment behaves as its name claims, so a recorded context is a declaration, trusted as a UDF's declarations are.
2. **What is recorded is the value in effect when the expression was declared, defaults included.** An omitted optional argument is an implicit parameter whose value the declaring engine supplied, and a record that notes only its absence leaves the next engine to supply its own. A geospatial distance function whose optional argument chooses planar, spherical or spheroidal computation is the plain case: an expression written without the argument means whichever baseline its author's engine defaulted to, and another engine with another default computes a different distance from the same text. The same holds for the session settings above, each of which is usually a default the author never chose. The record must therefore resolve every default at declaration and store the result, so that a later change of default, in an engine or in the specification, changes no stored expression's meaning.
3. **An expression that records nothing reads an unknown environment**, the worst case under rule 5 above. The floor of functions whose behavior the specification fixes needs no record, since the specification is their environment.
4. **Only some coeffects can be recorded usefully.** The rows of another table can be, as a snapshot ID, which is what a materialized view's refresh state records about its sources. A called function's definition can be, as its version. The current time can be, as the parameter engines already bind once per query: a query replayed with the time of its first run returns the same answer against the same snapshot. Recording it does not make a stored result current, because a consumer that asks whether the result is fresh wants the present time, and the record says only which time the result was computed for. Entropy cannot be recorded, and evaluation state only partly: a seed and a generator algorithm can be, but they fix only the start of a sequence whose position at any row depends on the schedule, which a different schedule cannot reuse.

## A declaration is a promise or a requirement

A declaration can be read in two directions. As a promise, it is a claim by whoever wrote it about the thing declared, for example that a function's body behaves a certain way, and a consumer that relies on it trusts the declarer. As a requirement, it is an instruction to whoever evaluates the expression, that it must evaluate in a certain way, and a consumer needs no trust to follow it, only the ability.

The UDF specification uses both readings without saying which applies, sometimes within one field. `on-null-input` is described as "an optimization hint", and its value `return-null` is phrased as a promise, that "the function always returns `NULL` if any input argument is `NULL`", which licenses an engine to skip evaluation. Its value `call` is phrased as a requirement, that "the engine must execute the function". Suppose a function declared `return-null` has a body that maps a null input to something else, through `coalesce` for example. An engine that reads the declaration as a requirement returns null without calling the body, one that reads it as a hint calls the body and returns the other value, and two conforming engines answer the same query differently. `secure` is a requirement on the engine, which "should prevent leakage", resting on a promise by the administrator, whose "responsibility" it is that secure functions are properly configured. `deterministic` is stated as a bare fact, "whether the function is deterministic", and the table specification requires it of UDFs in `check` constraints without saying who verifies it.

The two readings differ in what a consumer that does not understand a declaration should do, which is the polarity distinction again. A promise is a license: a consumer that ignores it forgoes an optimization and remains correct, so an unknown promise is safe to ignore. A requirement is an obligation: a consumer that ignores it evaluates something other than what was declared, so an unknown requirement must cause refusal. Many declarations are both. A recorded context is a requirement on the evaluator, to evaluate under this Unicode version, resting on a promise by the writer, that the stored index values were computed under it. In a materialized view's declared time dependency, the granularity is a promise by the author that licenses an engine to memoize, and binding the current time at refresh is a requirement on the refreshing engine.

The trust question therefore concerns promises only. A requirement asks of the consumer only that it meet the requirement or refuse. A promise needs either a consumer that can check it, as an engine that parses a body's dialect can check a UDF's declared properties against its body, or a decision about who answers for a false one. The specification should say of every declaration which reading it intends, and of every promise whether a consumer may rely on it to change a query's results or only to avoid work.

## Every consumer analyzes every node, and refuses what it does not understand

An implementation that meets a function it does not know, in an expression it is asked to evaluate, store or trust, can assume the best about it or refuse it, and assuming the best is how silent wrong answers happen. The rule this note proposes is refusal, stated formally as assuming the worst: an unknown function has every coeffect and every effect, so it fails every test a feature imposes, and the consumer takes whatever course the feature prescribes for an expression that fails. The obligation falls on every consumer, not only on writers, because the cost of a misunderstood expression usually lands on a reader.

What the prescribed course should be depends on how the consumer relies on the expression, and here the distinction between a hint that only speeds a query and one that changes its answer becomes sharp:

- **Where ignoring an expression costs only speed, a consumer that cannot analyze it ignores it.** A planner that cannot analyze the expression of an `expr-value` stats-only field does not use its statistics, and the scan reads files it might have skipped. The stats-only field rule already says readers must not fail on an unsupported field type; the same tolerance extends to an unsupported expression.
- **Where the consumer must act on the expression, it fails.** A writer that cannot evaluate a `write-default` cannot supply the field's value, and must refuse the write rather than write a null; the draft does not yet say so.
- **Where an expression is used as a hint that the planner trusts, an error in the analysis is an error in the answer.** A planner that matches a query's term to an index blob's input expression, or to an `expr-value` field's expression, concludes from statistics over the stored expression that some files cannot contain matching rows. If the stored expression named a function the planner resolves to a different definition, because the name is the same and the version or the dialect is not, the planner excludes files that contain matching rows. A planner that eliminates a predicate because a `check` constraint over it is `validated` is in the same position, and a UDF redefined since the constraint was validated turns that elimination into a wrong answer.

The third case is the one that makes the analysis urgent. Expressions entered Iceberg as things a writer evaluates, where a misunderstanding fails a write. They are now becoming things a planner trusts, through stats over expressions, index input expressions and constraint statuses, and in that role a misunderstanding produces a fast query with the wrong result. This is the polarity distinction of the [note on contracts](../contracts/README.md#appendix-b-dimensions-of-the-contract): a structure that only licenses a reader to skip work is safe to ignore and safe to misjudge conservatively, and one that licenses a conclusion about what the data contains needs an analysis that is exact, and reproducible across evaluators, before anyone trusts it.

## How a feature admits expressions

With the analysis defined centrally, a feature that admits expressions states its requirements as tests of the computed properties, and says what a consumer may rely on an expression for when it passes them and what the consumer does when it does not. For the consumers above, these might read:

| Feature | May read | May do | What a consumer may rely on it for | A consumer that refuses the expression |
|---|---|---|---|---|
| `write-default` | The clock and session context, if the feature pins which clock, which context, and when and how often the expression is evaluated | Produce a null only for an optional field; raise an error, which fails the write | Readers take the stored value as the field's value and never evaluate the expression again | Fails the write |
| `initial-default` | Nothing, after constant folding by the commit that adds the field | Nothing | Readers substitute the value for the field in rows written before it existed, and every reader substitutes the same one | Fails the schema change |
| `check` constraint | Fields of the current row; implementation tables and session settings only as recorded with the expression | Produce a null or a NaN, which the expressions specification's null-safe comparisons already interpret; an error needs a stated meaning | A writer rejects rows that fail it; a planner eliminates a predicate implied by a `validated` constraint, only if the definition versions it was validated against are current | A writer fails the write; a planner does not use the constraint |
| `expr-value` stats, index input expressions | Fields of the current row; implementation tables and session settings only as recorded with the expression | Produce a null; raise an error, if the stats or index record which rows erred | A planner skips files that the statistics or the index show cannot match, for a query term that matches the stored expression exactly under its recorded context | Ignores the statistics or the blob |
| Scan planning filter | Fields of the current row; session context, resolved by the client | Anything the engine can evaluate | A client reads only the files the service plans, and applies the residual the service returns, or computes its own where the service omits it | Evaluates the residual itself, or fails the query |

The alternative is an allowlist per feature, and the trouble with allowlists is that they are never finished. A list sized for today's use admits `upper` and `trim`, and then someone needs `concat`, then `substring`, then division, then `regex_match`, then `contains`, and each addition is a specification change, argued afresh in each feature's section, with the risk that two features admit the same function under different conditions. The analysis admits a function the day it declares its properties, in every feature whose tests those properties pass, and keeps it out of every feature whose tests they fail: `regex_match` declared as reading its dialect is admitted in a scan filter, where only one engine evaluates it, and in a stored index expression only with its dialect recorded, where a reader that cannot evaluate that dialect ignores the blob, without anyone writing either rule down.

An allowlist has one advantage, which is that its members' behavior is fixed by the specification and therefore portable. The two approaches combine well. The functions in `iceberg_functions`, and those in `sql_functions` that Iceberg chooses to define exactly, form a floor whose properties the specification fixes, and every conforming implementation must evaluate them identically; beyond the floor, functions describe themselves, and the analysis decides where each may go. This is the arrangement the [Puffin proposal](puffin-blob-types-and-compaction.md) makes for blob types, a small set of standard types beside an open namespace of self-describing ones, and it lets the vocabulary grow without each addition becoming a specification change.

## Changes, in three phases

Each phase is useful without the ones after it. The numbering runs across phases so that items can be cited.

**Phase 1: fence what already exists.** These changes need no vocabulary and almost no new metadata, and they close the paths to a wrong answer before stored expressions acquire trusting readers.

1. In the expressions specification, a requirement that a consumer refuse an expression containing a function it does not know, before evaluating, storing or trusting it, and take the course the feature carrying the expression prescribes.
2. In the table specification, for each existing feature (`write-default`, `initial-default`, `check` constraints and `expr-value` stats-only fields), what a consumer may rely on the expression for and what it does on refusal, including when and how often a `write-default` is evaluated ([prose fix 13](../contracts/prose-fixes.md)).
3. For `check` constraints, a decision on whether a planner may rely on a constraint's status, and if so, a requirement that the status record the definition versions of the UDFs its expression calls.
4. In the UDF specification, a statement that engines may rely on a declaration to change a query's results only if the declaration is part of the definition version the expression was analyzed against. Also a statement of whether `on-null-input: return-null` obliges an engine to return null or only licenses it to, since engines that read it differently give different answers for a function whose body disagrees with its declaration.

**Phase 2: a vocabulary, and declarations in it.** These let a feature admit a function by its properties instead of by name.

5. In the expressions specification, a section defining the property vocabulary, the computation over expression trees, and the rule that an unknown or undeclared function has every property.
6. Declared properties for every function in `iceberg_functions`, and for whichever `sql_functions` Iceberg defines, including the algebraic laws that license an engine to rewrite an expression.
7. In the UDF specification, property declarations on each definition version, of which `deterministic`, `return-nullable` and `on-null-input` become special cases or derived shorthands, covering the body and everything it calls, each stated as a promise, a requirement or both.
8. The rules of item 2 restated as tests of computed properties.

**Phase 3: recorded context.** This admits functions that depend on their environment into stored uses, for consumers that can reproduce the environment.

9. In the expressions specification, a way to record with a stored expression the values of the environmental coeffects it reads, with every default resolved, and a registry of names for those values.
10. For features that store expressions and are still being designed, such as index input expressions and a materialized view's [declared context dependencies](../contracts/materialized-views.md#candidate-text), recorded context from the start, since adding it later strands whatever was stored without it.

## Open questions

- **Who answers for a false promise.** An engine that can parse a dialect can check a body against the promises its definition makes; one that cannot must take them on faith or decline to rely on them where reliance changes answers. Which it should do is a policy question each feature may answer differently.
- **How fine the vocabulary should be.** Too coarse and it repeats the problem of `deterministic`; too fine and no one fills it in. The table above is a starting point, and the right granularity is whatever the tests of actual features need to distinguish.
- **What an error means in a predicate.** The predicate boundary settles what a null means in a `WHERE` clause and in a `CHECK` constraint, and leaves errors open. Whether an error in a `check` constraint is a violation, and whether one in a filter fails the query or excludes the row, needs the same treatment, per feature.
- **Whether engines will carry old environments.** Unicode case mapping and time zone rules change by design. A recorded version is exact, and under refusal a stale one costs speed rather than correctness, but an index whose expression records a Unicode version no current engine bundles is dead weight until rebuilt. Whether engines should keep old tables, and for how long, is a cost each implementation will weigh differently.
- **Where a context is recorded.** Recording it with each expression is exact and verbose; a table-level default that each expression may override is compact, and raises the question of what happens to stored expressions when the default changes.
