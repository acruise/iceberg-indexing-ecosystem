# Roadmap

*A top-down account of what this repository proposes and why, arranged by the strategic questions the proposals answer rather than by the documents that contain them. For each question it gives the reason for proposing anything, the mechanisms proposed, the problems in the [register](contracts/problems.md) they address, what remains open, and the broader direction that the mechanism would make possible if the community wanted to go further. It is a map of the other documents and adds no proposals of its own.*

**Author:** Alex Cruise  
**Updated:** November 13, 2026  
**Status:** working document; revise whenever a proposal changes status

## The through-line

Every document here makes one argument from a different side. Iceberg's specification is extensible in practice (new blob types, new sidecars, new formats, new metadata fields, new catalog endpoints), but most of the rules that keep an extension safe are not written down: whether an implementation that does not understand something may ignore it, what a rewrite must do with it, what maintenance must keep, what binds it to the data it describes. Implementations infer these rules, and the inference is correct only as long as every implementer infers the same thing. The proposals turn inferred rules into declared ones, a kind at a time, so that the next extension can be added without a new way of returning a wrong answer.

Two principles govern every choice, and a reader who rejects either will disagree with much of what follows. **Correctness comes before performance**: an operation that cannot establish what it needs degrades or refuses, and a wrong answer is never an allowable outcome. **Explicitness wherever ambiguity is possible**: where a reader would otherwise have to infer a rule, the rule is declared, and an empty declaration ("none") is written rather than left out.

Explicit does not mean machine-decidable. Every mechanism here is specified in normative prose written for people, with machine-readable declarations covering what a tool needs to decide whether to proceed. The prose says plainly which of its rules the declarations do not yet express, and where such a rule bears on safety the declaration takes the conservative value, so that a tool reading only the declaration refuses rather than guesses. Interactions between features, and departures from the specification a feature extends, are written down in that prose rather than modeled.

The repository holds two lines of work that arrived at this argument separately. The [Puffin proposal](proposals/puffin-blob-types-and-compaction.md) began with one concrete need, indexes built after the data and kept valid through compaction, and found each gap the need exposed. The [note on contracts](contracts/README.md) asked the same questions of data file formats, storage and commits, and found the same gaps elsewhere. The eight threads below draw on both.

## 1. What may be added, and by whom

**Why.** Iceberg has no managed namespace for the things third parties add. Blob types, property keys and format names are bare strings, and an implementation decides whether it supports something by matching a name, which says nothing about version or meaning. An open ecosystem of index types (or formats, or functions) is impossible without a way to name a type, publish what it means, and let an implementation that lacks it decline safely.

**Proposed.**

1. Namespaced blob type identifiers with the major version in the identifier, names without a namespace reserved for the specification, and a two-tier registry ([Puffin proposal §4](proposals/puffin-blob-types-and-compaction.md#4-blob-type-identifiers-and-the-registry); [phase 1](proposals/phase-1-open-blob-types.md)).
2. A machine-readable descriptor per blob type, published with the type (§5).
3. A Java service-provider interface through which engines discover type implementations at run time, with rules for implementations that cannot (§9).
4. The same identifier grammar for `file_format`, opening the list of data file formats ([note on contracts](contracts/README.md#a-namespace)).
5. A list of the features a table uses, introduced under version 4 as the last integer increment, each feature declaring for reading, writing and maintenance whether a component that lacks it may proceed ([feature versioning](contracts/feature-versioning.md)). Each feature is versioned in turn: its major version is in its identifier, and exact major matching is the safe floor, while compatible minor revisions, which only add, let a component of an earlier revision proceed in any role for which the table records no revision beyond its own ([versions of a feature](contracts/feature-versioning.md#versions-of-a-feature)). Versions become named sets of features, and every later extension, of whatever kind, is fenced by declaring it rather than by waiting for a new version. The list is computed rather than trusted: each snapshot records the closure of the features used by everything reachable from it, and the table records which retained snapshots use each feature, so that time travel, maintenance and the retirement of a deprecated format can each be decided per snapshot ([which features a snapshot uses](contracts/feature-versioning.md#which-features-a-snapshot-uses-computed-upward)).

**Addresses.**

- [E21](contracts/problems.md#e21-extension-identifiers-are-unmanaged): extension identifiers are unmanaged
- [E22](contracts/problems.md#e22-capabilities-are-inferred-from-a-name): capabilities are inferred from a name
- [E23](contracts/problems.md#e23-third-party-implementations-cannot-be-plugged-in): third-party implementations cannot be plugged in
- [V11](contracts/problems.md#v11-admitting-a-format-takes-a-specification-change-and-the-alternative-is-a-private-name): admitting a format takes a specification change, and the alternative is a private name (through the fourth item)
- [E30](contracts/problems.md#e30-every-format-change-is-fenced-by-refusing-the-whole-table): every format change is fenced by refusing the whole table (through the fifth item)

**If nothing is done.** Indexes and other extensions stay private to the engine that writes them. Each vendor ships its own blob types under bare names, so that a table's indexes serve only the engine that built them and the open format becomes a common floor beneath incompatible private layers, which is the fragmentation a shared specification exists to prevent. The worse case is a collision: two writers choose the same name for different encodings, and a reader that decides support by matching the name ([E22](contracts/problems.md#e22-capabilities-are-inferred-from-a-name "Capabilities are inferred from a name")) applies one type's payload as the other's, which for a structure that excludes files can exclude files that match.

**Status and next step.** Phase 1 of the [phasing plan](proposals/phasing.md) and the cheapest first ask: no format version, nothing changes for existing blobs. Registry governance is open (§14.15). The feature list is the opposite case, needing the version 4 increment, and it matters beyond this thread: it is the fallback that relieves the version 4 deadline on everything else (see Sequencing).

**With sufficient bravery.** The feature list's envelope could describe every kind of thing a component can fail to understand, table features, formats, format extensions, sidecar kinds and functions alike, under one identifier space. Beyond that, the feature-versioning note's own TODO imagines declarations of reliance and scope as predicates over a versioned vocabulary of operation properties, and the set of kinds opened to third parties; it records both without proposing them.

## 2. What survives a rewrite

**Why.** Compaction is the most common write a table sees, and today everything attached to the files it replaces is lost or must be recomputed by a job nobody standardizes. Statistics files are bound to a snapshot and do not follow compaction ([E24](contracts/problems.md#e24-metadata-attached-to-data-files-does-not-survive-compaction "Metadata attached to data files does not survive compaction")); a writer that replaces shared metadata discards what it does not understand ([E25](contracts/problems.md#e25-shared-metadata-is-replaced-whole-by-writers-that-understand-only-part-of-it "Shared metadata is replaced whole by writers that understand only part of it")); an index pinned to a snapshot is disabled by every rewrite ([V14](contracts/problems.md#v14-each-rewrite-disables-a-snapshot-pinned-index-until-it-is-rebuilt "Each rewrite disables a snapshot-pinned index until it is rebuilt")); and each kind of sidecar has its rewrite rule written separately ([V12](contracts/problems.md#v12-each-kind-of-sidecar-needs-its-own-rewrite-rule "Each kind of sidecar needs its own rewrite rule")). An index built late, after the workload is known, is worthless if the next compaction erases it, and the choice of index is otherwise fixed when the data is written ([E29](contracts/problems.md#e29-the-choice-of-index-is-fixed-when-the-data-is-written "The choice of index is fixed when the data is written")).

**Proposed.**

1. Data-file-scoped blobs, valid for as long as the data file they describe is live, with a derivation rule that confines their content to the file and its configuration ([Puffin proposal §6](proposals/puffin-blob-types-and-compaction.md#6-data-file-scoped-blobs)).
2. Compaction modes declared per type (`drop`, `rebuild`, `merge`, `retain`), with unknown types treated as `drop` and losses reported in the snapshot summary, offered as candidate specification text (§8).
3. A rule that a writer replacing a statistics file copies forward blobs of types it does not recognize ([phase 1, §3.4](proposals/phase-1-open-blob-types.md)).
4. Positions fixed when a file is written, so that deletion vectors and row lineage cannot be misapplied ([prose fix 9](contracts/prose-fixes.md)).

**Addresses.**

- [E24](contracts/problems.md#e24-metadata-attached-to-data-files-does-not-survive-compaction): metadata attached to data files does not survive compaction
- [E29](contracts/problems.md#e29-the-choice-of-index-is-fixed-when-the-data-is-written): the choice of index is fixed when the data is written
- [V14](contracts/problems.md#v14-each-rewrite-disables-a-snapshot-pinned-index-until-it-is-rebuilt): each rewrite disables a snapshot-pinned index until it is rebuilt (for negative indexes)
- [V12](contracts/problems.md#v12-each-kind-of-sidecar-needs-its-own-rewrite-rule): each kind of sidecar needs its own rewrite rule (as a model for every kind)
- [E25](contracts/problems.md#e25-shared-metadata-is-replaced-whole-by-writers-that-understand-only-part-of-it): shared metadata is replaced whole by writers that understand only part of it (in part: the loss becomes defined and visible, not prevented)
- [E13](contracts/problems.md#e13-row-positions-are-not-required-to-be-stable): row positions are not required to be stable

**If nothing is done.** Every compaction quietly discards the index and statistics coverage built on the files it rewrites, so operators must choose between compacting and indexing, and an index built after the data, the case this repository was written for, never pays for itself. The loss is silent: a planner that finds no blob plans without one, and nobody learns that the statistics they paid for are gone. The sharper risk is [E13](contracts/problems.md#e13-row-positions-are-not-required-to-be-stable "Row positions are not required to be stable"): a reader that numbers a file's rows differently from its writer applies deletion vectors to the wrong rows, and returns a wrong answer with no error.

**Status and next step.** Phase 3, which waits on a hosting decision: whether data-file-scoped blobs can be carried as a second index type under the community's secondary index specification ([pull request 16961](https://github.com/apache/iceberg/pull/16961); Puffin proposal §12.3 and §14.3). That question has not yet been put to the specification's authors, and it is the critical path for the whole line.

**With sufficient bravery.** Section 14.18 of the Puffin proposal sketches invalidation finer than a whole blob: first recording the deletion vector a blob was computed under, then sets of invalidated rows keyed by `_row_id`, and eventually the re-binding of blobs to the files a rewrite moved their rows into, as Lance remaps index addresses. It would require cooperation from writers, a record of which columns an update changed, and relaxing the proposal's non-goal of describing only files. Blobs spanning several files (§14.12) are the companion direction, and the hardest part of it is compaction.

## 3. What maintenance must know

**Why.** Orphan removal treats every file beneath the table location that snapshot metadata does not reference as garbage, and expiration and purge know only what metadata lists ([E17](contracts/problems.md#e17-maintenance-learns-what-to-keep-only-from-snapshot-metadata "Maintenance learns what to keep only from snapshot metadata")). Iceberg has been through this once, when statistics files took four releases of the Java implementation to become safe from its own maintenance ([note on index reachability](proposals/index-reachability.md)). The secondary index specification under review keeps index metadata outside table metadata and, as drafted, a conforming version 4 implementation may delete every index beneath the table location in one run ([V13](contracts/problems.md#v13-conforming-version-4-maintenance-may-delete-indexes "Conforming version 4 maintenance may delete indexes")). The remedy is cheapest before version 4 is published, which makes this the most time-sensitive thread.

**Proposed.**

1. A placement rule: an unreferenced Puffin file lives outside the table location, sharing no string prefix with it (phase 1).
2. A discovery chain, a numbered sequence of metadata files under a root of its own that advances by conditional create and records the table's UUID (Puffin proposal §6.5). The Iceberg REST Catalog is the expected commit authority for an index wherever it implements the index endpoints; the chain is the floor for catalogs that do not.
3. A list of discovery roots in version 4 table metadata, with four obligations on maintenance: orphan removal spares the roots, expiration may invoke a collector, purge removes them, and copying a table says what happens to them ([decoupled index metadata](proposals/decoupled-index-metadata.md); [version 4 ask 3](contracts/v4-asks.md#3-declaring-what-a-snapshot-depends-on)).
4. The name *sidecar* for the class of files that hang from the files they describe, with two constraints every existing kind already obeys: a required sidecar is referenced and committed with its subjects, and a discovered sidecar must be ignorable ([sidecars](contracts/sidecars.md)).

**Addresses.**

- [E17](contracts/problems.md#e17-maintenance-learns-what-to-keep-only-from-snapshot-metadata): maintenance learns what to keep only from snapshot metadata
- [V13](contracts/problems.md#v13-conforming-version-4-maintenance-may-delete-indexes): conforming version 4 maintenance may delete indexes
- [E31](contracts/problems.md#e31-ownership-of-data-files-is-decided-for-the-whole-table): ownership of data files is decided for the whole table (in part, through per-file ownership)
- [V2](contracts/problems.md#v2-nothing-shows-how-much-of-a-table-remains-in-a-deprecated-format): nothing shows how much of a table remains in a deprecated format (in part, through the declaration of live formats)

**If nothing is done.** The first run of a conforming version 4 orphan removal against a table with indexes beneath its location deletes them all, and the failure is invisible, since a planner that finds no index simply plans without it ([V13](contracts/problems.md#v13-conforming-version-4-maintenance-may-delete-indexes "Conforming version 4 maintenance may delete indexes")). Once version 4 is published, the fix becomes a change in behavior that no format version fences, adopted engine by engine over several releases, as the handling of statistics files was. This is the one thread with a deadline.

**Status and next step.** The list of discovery roots is the single most valuable ask in the repository and should be raised first with the index specification's authors, independently of everything else. Its deadline is version 4 only if version 4 lacks a feature list that maintenance consults before deleting; with one, the roots can follow as a later feature (thread 1). The sidecar proposal is editorial and can proceed in parallel.

**With sufficient bravery.** A maintenance-capability fence, modeled on Delta's protocol check for `VACUUM`, under which a table declares the maintenance capabilities it needs and maintenance that lacks one refuses ([index reachability](proposals/index-reachability.md)), was once the bold version of this thread; the feature list of thread 1 now carries it, as the requirement that maintenance read the list before deleting. Beyond that, the sidecar proposal's "waypoint" (one descriptor envelope for every stored object, metadata files included, with blob type descriptors as one instance) would let maintenance reason about any stored object from its declaration rather than from code written for its kind.

## 4. What a component may ignore

**Why.** Whenever a component meets something it does not understand, it must either proceed as though the thing were absent or stop, and the correct choice is a property of the thing, not the component. The specification makes this decision case by case, and for deletion vectors and column files does not make it at all: nothing says a reader must apply them, though a reader that skipped either would return wrong rows ([E11](contracts/problems.md#e11-whether-an-unsupported-thing-may-be-ignored-is-decided-case-by-case "Whether an unsupported thing may be ignored is decided case by case"), [V5](contracts/problems.md#v5-a-reader-that-ignores-a-column-file-returns-wrong-values "A reader that ignores a column file returns wrong values")). Defaults raise the same question for readers that cannot supply them and writers that cannot evaluate them ([E12](contracts/problems.md#e12-a-reader-that-cannot-supply-a-default-has-no-stated-obligation "A reader that cannot supply a default has no stated obligation"), [V7](contracts/problems.md#v7-a-writer-that-cannot-evaluate-a-default-has-no-stated-obligation "A writer that cannot evaluate a default has no stated obligation")), and unsupported formats and features are discovered partway through a scan ([E16](contracts/problems.md#e16-unsupported-formats-and-features-are-discovered-mid-scan "Unsupported formats and features are discovered mid-scan"), [E28](contracts/problems.md#e28-a-reader-cannot-tell-whether-it-can-decode-a-data-file-before-opening-it "A reader cannot tell whether it can decode a data file before opening it")).

**Proposed.**

1. Prose fixes that state reliance where it is implied: readers must apply deletion vectors and projected column files; a reader that cannot supply a default fails; a writer that cannot evaluate one fails; ignoring is the exception ([prose fixes 5 to 8](contracts/prose-fixes.md)).
2. Reliance declared per kind and, where a kind cannot decide, per instance in the reference, so that a reader can find it without understanding the thing referred to; an instance may strengthen its kind's reliance and never weaken it ([note on contracts](contracts/README.md#reliance-when-a-reader-may-ignore-a-sidecar)).
3. A table-level declaration of the formats and required sidecar kinds a snapshot uses, so that a reader can refuse at load time rather than mid-scan (version 4 ask 3).
4. Declared outcomes for degradations, observable to the operator and detectable at commit (the note's degradation requirements).

**Addresses.**

- [E11](contracts/problems.md#e11-whether-an-unsupported-thing-may-be-ignored-is-decided-case-by-case): whether an unsupported thing may be ignored is decided case by case
- [E12](contracts/problems.md#e12-a-reader-that-cannot-supply-a-default-has-no-stated-obligation): a reader that cannot supply a default has no stated obligation
- [E16](contracts/problems.md#e16-unsupported-formats-and-features-are-discovered-mid-scan): unsupported formats and features are discovered mid-scan
- [E28](contracts/problems.md#e28-a-reader-cannot-tell-whether-it-can-decode-a-data-file-before-opening-it): a reader cannot tell whether it can decode a data file before opening it
- [V5](contracts/problems.md#v5-a-reader-that-ignores-a-column-file-returns-wrong-values): a reader that ignores a column file returns wrong values
- [V7](contracts/problems.md#v7-a-writer-that-cannot-evaluate-a-default-has-no-stated-obligation): a writer that cannot evaluate a default has no stated obligation
- [V2](contracts/problems.md#v2-nothing-shows-how-much-of-a-table-remains-in-a-deprecated-format): nothing shows how much of a table remains in a deprecated format (in part)

**If nothing is done.** Correctness rests on every implementer inferring the same rule from semantics the specification never states. An implementation that infers differently, typically a new one in a language other than Java, skips a deletion vector or a column file it does not support and returns deleted rows or wrong values without an error ([E11](contracts/problems.md#e11-whether-an-unsupported-thing-may-be-ignored-is-decided-case-by-case "Whether an unsupported thing may be ignored is decided case by case"), [V5](contracts/problems.md#v5-a-reader-that-ignores-a-column-file-returns-wrong-values "A reader that ignores a column file returns wrong values")). Where the failure is safe, it is still late: an unsupported format or feature is discovered partway through a scan, after the work before it has been spent ([E16](contracts/problems.md#e16-unsupported-formats-and-features-are-discovered-mid-scan "Unsupported formats and features are discovered mid-scan")).

**Status and next step.** The prose fixes are drafted and need no format change, though prose fix 8 would make some current behavior non-conforming and should follow an audit. Reliance in the reference needs a format change and is deliberately not requested until two kinds of sidecar need it.

**With sufficient bravery.** The note's Appendix B treats a deployment (engine, catalog, formats, `FileIO`, storage) as a graph whose edges each carry a verdict of safe, degraded, refused or undeclared, computed from declarations made at each layer, with requirements flowing down a must-understand channel and verdicts flowing up, including through the REST planning response. If the dimensions of the contract were lattices, the verdict for a whole read would be the join of its parts. The note treats this as a goal, not a proposal, and is candid that several dimensions resist ordering.

## 5. What binds data to the metadata that describes it

**Why.** A deletion vector, a row id and a manifest's metrics are committed once and trusted thereafter, so the relationships they depend on (a path to a file, or a position to a row) must hold for the life of the file. Several do not: paths may be reused ([E5](contracts/problems.md#e5-paths-may-be-reused "Paths may be reused")), a file overwritten in place is detectable only if its length changed ([E6](contracts/problems.md#e6-out-of-band-mutation-is-detectable-only-by-a-change-of-length "Out-of-band mutation is detectable only by a change of length")), row positions are not required to be stable across readers ([E13](contracts/problems.md#e13-row-positions-are-not-required-to-be-stable "Row positions are not required to be stable")), and relocation, made routine by relative paths in version 4, breaks identity based on location ([V9](contracts/problems.md#v9-relocation-becomes-routine-and-location-based-identity-does-not-survive-it "Relocation becomes routine, and location-based identity does not survive it")). Column files depend on position more heavily than anything else in the table ([V6](contracts/problems.md#v6-a-column-file-is-bound-to-its-data-file-by-location "A column file is bound to its data file by location")).

**Proposed.**

1. A binding protocol of five rules: fixed by the commit, durable and memorialized, immutable or versioned, independent of the reader, verifiable ([note on contracts, Appendix E](contracts/README.md#appendix-e-bindings-between-a-file-and-the-metadata-that-tracks-it)).
2. Paths not reused, and positions fixed at write (prose fixes 3 and 9).
3. A content hash on tracked files, column files and deletion vectors ([version 4 ask 1](contracts/v4-asks.md#1-a-content-hash-on-tracked-files)).

**Addresses.**

- [E5](contracts/problems.md#e5-paths-may-be-reused): paths may be reused
- [E6](contracts/problems.md#e6-out-of-band-mutation-is-detectable-only-by-a-change-of-length): out-of-band mutation is detectable only by a change of length
- [E13](contracts/problems.md#e13-row-positions-are-not-required-to-be-stable): row positions are not required to be stable
- [V6](contracts/problems.md#v6-a-column-file-is-bound-to-its-data-file-by-location): a column file is bound to its data file by location
- [V9](contracts/problems.md#v9-relocation-becomes-routine-and-location-based-identity-does-not-survive-it): relocation becomes routine, and location-based identity does not survive it

**If nothing is done.** A data file replaced at the same path, by an operator, a tool, a lifecycle policy or a copy, keeps its deletion vectors and row ids, which then apply to rows they were never written for. Unless the length changed, nothing detects it, and afterward nothing can show that it happened ([E6](contracts/problems.md#e6-out-of-band-mutation-is-detectable-only-by-a-change-of-length "Out-of-band mutation is detectable only by a change of length")). Version 4 makes this more likely, not less, by making relocation routine ([V9](contracts/problems.md#v9-relocation-becomes-routine-and-location-based-identity-does-not-survive-it "Relocation becomes routine, and location-based identity does not survive it")).

**Status and next step.** The content hash is an optional version 4 field and should be raised while version 4 is open; the prose fixes can go at any time.

**With sufficient bravery.** Storage as a part of the specification in its own right, with capability tiers (read, write, commit, maintain) declared per `FileIO` and backing store, in place of the single sentence the specification now devotes to what it requires of a file system. [E8](contracts/problems.md#e8-several-strings-can-name-one-object "Several strings can name one object"), [E9](contracts/problems.md#e9-orphan-removal-races-with-commits-and-compares-clocks "Orphan removal races with commits and compares clocks") and [E10](contracts/problems.md#e10-lifecycle-policies-archival-classes-and-credential-scope "Lifecycle policies, archival classes and credential scope") (several names for one object, orphan removal racing commits on clocks, lifecycle policies and credential scope) have no proposed solution yet, and would find their home there.

## 6. How commits are trusted

**Why.** The specification's list of conditions a retried commit must check predates deletion vectors, so a compaction racing a row-level delete can resurrect deleted rows in any implementation that follows the text alone ([E1](contracts/problems.md#e1-the-retry-conditions-omit-row-level-deletes "The retry conditions omit row-level deletes")). The window a retry must validate is unstated ([E2](contracts/problems.md#e2-the-validation-window-and-what-to-do-outside-it-are-unstated "The validation window, and what to do outside it, are unstated")), validation is enforced by nothing outside the writer and cannot be checked afterward ([E3](contracts/problems.md#e3-validation-is-enforced-by-nothing-outside-the-writer-and-is-undetectable-afterward "Validation is enforced by nothing outside the writer, and is undetectable afterward")), and a commit of unknown outcome can be retried blindly ([E4](contracts/problems.md#e4-commits-of-unknown-outcome "Commits of unknown outcome")). Meanwhile Iceberg has decided, in effect from version 4, that every commit goes through a catalog, in practice the Iceberg REST Catalog ([catalogs](contracts/catalogs.md); [V10](contracts/problems.md#v10-no-catalog-free-commit-protocol-remains "No catalog-free commit protocol remains")).

**Proposed.**

1. Retry conditions that cover deletion vectors and column files, with an exception admitting compactors that carry concurrent deletes forward instead of aborting ([prose fix 1](contracts/prose-fixes.md#1-retry-conditions-for-deletion-vectors-and-column-files)).
2. Validation against every intervening commit, and atomic exclusive create or nothing (prose fixes 2 and 4).
3. The read base of each snapshot recorded in metadata, so that validation can be checked after the fact ([version 4 ask 2](contracts/v4-asks.md#2-the-read-base-of-each-snapshot)).
4. A plain statement that version 4 requires a catalog, with the Iceberg REST Catalog as the de facto requirement, and with each proposal here saying what it assumes of one (catalogs).

**Addresses.**

- [E1](contracts/problems.md#e1-the-retry-conditions-omit-row-level-deletes): the retry conditions omit row-level deletes
- [E2](contracts/problems.md#e2-the-validation-window-and-what-to-do-outside-it-are-unstated): the validation window, and what to do outside it, are unstated
- [E3](contracts/problems.md#e3-validation-is-enforced-by-nothing-outside-the-writer-and-is-undetectable-afterward): validation is enforced by nothing outside the writer, and is undetectable afterward
- [E4](contracts/problems.md#e4-commits-of-unknown-outcome): commits of unknown outcome (in part)
- [E7](contracts/problems.md#e7-exclusive-create-is-not-atomic): exclusive create is not atomic
- [V4](contracts/problems.md#v4-the-retry-conditions-do-not-cover-column-files): the retry conditions do not cover column files
- [V10](contracts/problems.md#v10-no-catalog-free-commit-protocol-remains): no catalog-free commit protocol remains (recast as decided)

**If nothing is done.** An implementation that follows the specification's text, rather than the Java implementation's behavior, resurrects deleted rows whenever a compaction races a row-level delete ([E1](contracts/problems.md#e1-the-retry-conditions-omit-row-level-deletes "The retry conditions omit row-level deletes")), and nobody can audit afterward which commits validated what ([E3](contracts/problems.md#e3-validation-is-enforced-by-nothing-outside-the-writer-and-is-undetectable-afterward "Validation is enforced by nothing outside the writer, and is undetectable afterward")). On the catalog side, operators learn of their dependence on the coordinator during an outage or a restore, when a table cannot be read because the only record of its current state, or of its location, was in a service that is down or was not backed up.

**Status and next step.** Prose fix 1 is the strongest single item in the contracts line, since it closes a correctness gap that the Java implementation already handles and the specification does not. The catalogs note's questions are clarifications and can be asked at any time.

**With sufficient bravery.** A catalog that sees every commit can enforce validation itself, which would make several of the commit requirements cheap to meet by asking one server rather than every writer (catalogs, implication 7). Serializable isolation could be made checkable by recording a commit's predicate (commit requirement 4, which no problem in the register yet cites). The storage-only commit protocol the note once proposed as a requirement survives as a floor for deployments that need one.

## 7. What derived state means

**Why.** An index, a statistic or a default is computed under parameters, and if those parameters are not recorded with the result, a reader cannot tell whether two results are comparable or whether one still answers today's question. Format parameters that change what the bytes mean are kept outside the bytes ([E27](contracts/problems.md#e27-parameters-that-change-what-the-bytes-mean-are-kept-outside-the-bytes "Parameters that change what the bytes mean are kept outside the bytes")), statistics from a defective writer are trusted indefinitely ([E26](contracts/problems.md#e26-statistics-from-a-defective-writer-are-trusted-indefinitely "Statistics from a defective writer are trusted indefinitely")) and in version 4 may become answers rather than hints ([V15](contracts/problems.md#v15-statistics-declared-tight-become-answers "Statistics declared tight become answers")), and defaults that are expressions depend on context that nothing records ([V8](contracts/problems.md#v8-defaults-depend-on-context-that-nothing-records "Defaults depend on context that nothing records")). The Puffin proposal's case is workload drift: the predicates a table serves move away from the indexes chosen for it, and a configuration that cannot be identified cannot be compared with the one the workload now needs.

**Proposed.**

1. Build configurations identified by a digest over the schema and a canonical encoding of the configuration, carried in-band or in a store, with readers that cannot resolve a configuration declining the blob ([Puffin proposal §7](proposals/puffin-blob-types-and-compaction.md#7-build-configurations)).
2. No evaluation parameters added to a type after its first version (§11.4), the one hard coupling between phases 1 and 2.
3. Expressions as inputs, using the version 4 expressions specification (§7.8).
4. Writer identity in per-file descriptions, with a table-level list of revoked writer versions, and functions that declare whether they read their evaluation context ([note on contracts](contracts/README.md); prose fix 13).

**Addresses.**

- [E26](contracts/problems.md#e26-statistics-from-a-defective-writer-are-trusted-indefinitely): statistics from a defective writer are trusted indefinitely
- [E27](contracts/problems.md#e27-parameters-that-change-what-the-bytes-mean-are-kept-outside-the-bytes): parameters that change what the bytes mean are kept outside the bytes
- [V7](contracts/problems.md#v7-a-writer-that-cannot-evaluate-a-default-has-no-stated-obligation): a writer that cannot evaluate a default has no stated obligation (in part)
- [V8](contracts/problems.md#v8-defaults-depend-on-context-that-nothing-records): defaults depend on context that nothing records
- [V15](contracts/problems.md#v15-statistics-declared-tight-become-answers): statistics declared tight become answers
- workload drift, which the register does not number

**If nothing is done.** A structure built under one configuration is used under another: a Bloom filter built with one normalization is consulted for a predicate normalized differently, and it excludes files that match. A defect in one writer's statistics persists for as long as the files it wrote ([E26](contracts/problems.md#e26-statistics-from-a-defective-writer-are-trusted-indefinitely "Statistics from a defective writer are trusted indefinitely")), and once version 4 lets statistics be declared tight, the same defect becomes a wrong answer to an aggregate query rather than a missed opportunity to prune ([V15](contracts/problems.md#v15-statistics-declared-tight-become-answers "Statistics declared tight become answers")).

**Status and next step.** Phase 2 for configurations and phase 4 for expressions. The writer-identity fields need manifest changes that no version 4 ask yet carries.

**With sufficient bravery.** Expressions classified by what they read and what they can do (their coeffects and effects), with functions declaring both, so that a planner can decide which defaults, index expressions and constraints are portable without a closed list of functions. Further out, lookup-table functions resolved by digest would let cardinality-reducing expressions be indexed without agreeing on every function's semantics across engines (Puffin proposal §14.8).

## 8. Which formats may be written, and which must still be read

**Why.** Version 4 is deciding two things about data file formats at once, and neither can be decided well without a written statement of what a format owes Iceberg ([E18](contracts/problems.md#e18-what-a-format-owes-iceberg-is-unwritten "What a format owes Iceberg is unwritten")). On the dev list it has been [proposed](https://lists.apache.org/thread/5jfzckl0cc9z683kz9vfv41pmhrm1tdb) that version 4 stop writing ORC and Avro data files while keeping existing ones readable, and the same proposal asks what bar a format should meet to become writable again. In the preceding discussion, Vortex, Lance and Nimble were named as formats worth keeping room for, and the File Format API has since made formats pluggable in the Java implementation. Stopping a format and starting one are the same question asked from opposite ends: what a format must provide to be read, what more it must provide to be written, and what Iceberg owes the files whose format it no longer writes.

**Proposed.**

1. A read tier and a write tier for formats: the read tier as the bar both for admitting a new format and for keeping a deprecated one readable, and the write tier as the further bar for becoming writable ([what a readable format provides](contracts/README.md#what-a-readable-format-provides); [what a writable format provides](contracts/README.md#what-a-writable-format-provides); [read-only support](contracts/README.md#read-only-support)).
2. If version 4 stops writing ORC and Avro, a statement that its readers must still read them under the same rules as any other format, default values included, so that the cost of the read obligation is visible when the decision is taken ([prose fix 12](contracts/prose-fixes.md#12-if-version-4-stops-writing-orc-and-avro-data-files)).
3. Ways to keep that obligation from growing: a small read tier, so that defaults, type promotion and constants are supplied once above every format rather than by each format's reader; refusing table changes that a live read-only file cannot honor, as the approved but unmerged [pull request 13060](https://github.com/apache/iceberg/pull/13060) proposed; and a record of which formats are live in a table ([the read obligation keeps growing](contracts/README.md#the-read-obligation-keeps-growing); [version 4 ask 3](contracts/v4-asks.md#3-declaring-what-a-snapshot-depends-on)).
4. `file_format` as an open namespace under the blob identifier grammar, with a registry and a descriptor per format, so that a format such as Vortex can be declared and read by those who implement it without waiting for a specification release ([a namespace](contracts/README.md#a-namespace)).
5. Format sidecars for what a format cannot hold natively, such as field ids and type annotations, and type mappings that state their ranges and what happens outside them ([sidecars for format integration](contracts/README.md#sidecars-for-format-integration); [E19](contracts/problems.md#e19-type-mappings-state-no-ranges-and-no-behavior-outside-them "Type mappings state no ranges, and no behavior outside them")).

**Addresses.**

- [V1](contracts/problems.md#v1-the-read-obligation-on-deprecated-formats-keeps-growing): the read obligation on deprecated formats keeps growing
- [V2](contracts/problems.md#v2-nothing-shows-how-much-of-a-table-remains-in-a-deprecated-format): nothing shows how much of a table remains in a deprecated format
- [E12](contracts/problems.md#e12-a-reader-that-cannot-supply-a-default-has-no-stated-obligation): a reader that cannot supply a default has no stated obligation (made worse by deprecation, since the Java ORC reader cannot supply defaults)
- [V3](contracts/problems.md#v3-there-is-no-bar-for-making-a-format-writable-again): there is no bar for making a format writable again
- [V11](contracts/problems.md#v11-admitting-a-format-takes-a-specification-change-and-the-alternative-is-a-private-name): admitting a format takes a specification change, and the alternative is a private name
- [E18](contracts/problems.md#e18-what-a-format-owes-iceberg-is-unwritten): what a format owes Iceberg is unwritten
- [E19](contracts/problems.md#e19-type-mappings-state-no-ranges-and-no-behavior-outside-them): type mappings state no ranges, and no behavior outside them
- [E28](contracts/problems.md#e28-a-reader-cannot-tell-whether-it-can-decode-a-data-file-before-opening-it): a reader cannot tell whether it can decode a data file before opening it
- [E21](contracts/problems.md#e21-extension-identifiers-are-unmanaged): extension identifiers are unmanaged (for formats, through the namespace)
- [E20](contracts/problems.md#e20-pushdown-semantics-are-reimplemented-for-each-format): pushdown semantics are reimplemented for each format (in part, through the division of labor in pushdown)

**If nothing is done.** On the stopping side, deprecation saves less than it appears to. Every later feature that changes how an existing file is interpreted, a default value or a type promotion, must be implemented by every reader of ORC and Avro in every language, or those readers must refuse; the Java ORC reader already cannot supply defaults, so adding a column with a default to a table that still holds ORC files makes every read that projects the column fail partway through a scan ([V1](contracts/problems.md#v1-the-read-obligation-on-deprecated-formats-keeps-growing "The read obligation on deprecated formats keeps growing"), [E12](contracts/problems.md#e12-a-reader-that-cannot-supply-a-default-has-no-stated-obligation "A reader that cannot supply a default has no stated obligation")). Nobody can tell when a table's last ORC file is gone ([V2](contracts/problems.md#v2-nothing-shows-how-much-of-a-table-remains-in-a-deprecated-format "Nothing shows how much of a table remains in a deprecated format")), so the ORC reader can never be retired with confidence, and the maintenance that deprecation was meant to save continues indefinitely on the read side. On the starting side, each new format either waits for a vote and a specification release before a table may hold a single file in it, or ships under a private `file_format` string that only its vendor's engines can read ([V11](contracts/problems.md#v11-admitting-a-format-takes-a-specification-change-and-the-alternative-is-a-private-name "Admitting a format takes a specification change, and the alternative is a private name")). The bar for becoming writable is argued afresh for each format because it was never written down ([V3](contracts/problems.md#v3-there-is-no-bar-for-making-a-format-writable-again "There is no bar for making a format writable again")), and type mappings without stated ranges let the same value come back differently through different formats ([E19](contracts/problems.md#e19-type-mappings-state-no-ranges-and-no-behavior-outside-them "Type mappings state no ranges, and no behavior outside them")).

**Status and next step.** The dev list proposal had one reply by November 13, which supported dropping ORC and Avro writes but named remaining "open to other formats in the write path" as the chief challenge of having one write format. The note's read and write tiers are the substantive answer both to that challenge and to the proposal's question about a bar for writability. A reply there is the next step, offering the tiers as that bar and prose fix 12 for whichever way the deprecation is decided; pull request 13060 could be revived alongside it. Both halves of this thread are on the version 4 clock, since the deprecation is a version 4 decision and the namespace for `file_format` is cheapest to introduce before version 4 fixes the list.

**With sufficient bravery.** Under [feature versioning](contracts/feature-versioning.md), formats and their extensions (an encoding, for instance) become features a table declares, each with its own reliance, so that a reader lacking Vortex refuses at load time the tables that contain it and serves every other, and retiring ORC becomes the removal of a feature rather than a property of a version boundary. Beyond that lies the distinction the note leaves open between the capabilities of a format and those of an implementation of it, such as a library that reads Vortex but cannot shred variants, which would let a deployment's verdict for a read be computed from what its particular libraries can do.

## Sequencing

The asks fall into three groups by what they cost and when they must be made, with a fallback should the version 4 asks be declined.

**Now, independently of each other.**

1. The list of discovery roots, put to the index specification's authors (thread 3). Time-sensitive: it must reach version 4.
2. Prose fix 1 and the other prose fixes, in small batches (threads 4 to 6).
3. Phase 1 of the Puffin proposal (thread 1).
4. The sidecar label and template (thread 3), editorial.
5. The catalogs note's questions (thread 6), as clarifications.
6. A reply to the dev list proposal to stop writing ORC and Avro (thread 8), offering the read and write tiers as the bar it asks for and prose fix 12 as the statement of what deprecation leaves behind.

**While version 4 is open.** The three version 4 asks (content hash, read base, dependency declaration), and the feature list. Several mechanisms in the note need manifest fields that none of the asks yet carries (per-file ownership, writer identity, reliance in the reference); either an ask should carry them or the documents should say they are deferred past version 4.

**If the concrete version 4 asks are declined.** The version 4 timeline is short, and the community may take none of the asks above. One ask is then worth spending everything on, because it turns every other version 4 deadline into an ordinary later feature: the feature list, with four things riding it ([feature versioning](contracts/feature-versioning.md#the-one-increment-the-mechanism-needs)).

1. Refusal, in every role, of any feature that is required for that role and not recognized.
2. Maintenance that reads the list before deleting or moving any file. Without this, nothing added later can protect files outside table metadata from conforming version 4 maintenance, and the deadline of thread 3 stands; with it, the list of discovery roots can follow as a feature.
3. One real user in version 4 itself, so that the mechanism is not speculative. The declaration of live data file formats is the natural one, since the deprecation of ORC and Avro writes needs it anyway (thread 8).
4. A list of tombstoned features in table metadata, defined as part of the feature list, so that every version 4 component consults it. A feature found unsafe after version 4 ships can then be withdrawn from every table that uses it, including by components whose descriptors are compiled in; without the list, only tombstones of individual revisions, enforced by raising a table's recorded revision, reach those components ([tombstones](contracts/feature-versioning.md#tombstones)).

The fallback does not relieve everything. The prose fixes never needed a version and should go regardless, and an ambiguity that version 4 ships, such as the unstated convention for supplying a table's location (thread 6), cannot be withdrawn by a later feature.

**After a hosting decision.** Phases 2 to 4 of the Puffin proposal, which depend on whether data-file-scoped blobs can live under the community's index specification.

The directions marked "with sufficient bravery" come last and should be raised only once the asks they generalize have been accepted, since each is easier to argue as the extension of something already agreed than as a design in its own right.

## Known inconsistencies between the documents

A review of the public documents on November 13 found several inconsistencies, most of which were fixed the same day: stale passages in the full Puffin proposal from before index manifests moved into the discovery chain (including the ordering and concurrency rules of its Sections 8.5 and 8.6), the treatment of blob types under feature versioning, the `config` and `scope` members of descriptors, the problems version 4 ask 3 addresses, and the framing of the object-store commit authority as a floor. What remains:

- The documents are written against different commits of apache/iceberg (`26c9544` for the register, the prose fixes and the note on contracts; `0cb5041` for the note on catalogs), and should be brought to a common baseline before circulation.
- The contracts prior-art survey does not yet cover [E30](contracts/problems.md#e30-every-format-change-is-fenced-by-refusing-the-whole-table "Every format change is fenced by refusing the whole table") or [E31](contracts/problems.md#e31-ownership-of-data-files-is-decided-for-the-whole-table "Ownership of data files is decided for the whole table"), which were added to the register after it was written.
- A descriptor's identifier member is `type` in the Puffin proposal and `id` in the feature-versioning envelope; harmless while the two are separate, and to be settled if blob types move under the envelope.
